# 意味解析
- task2で作成したASTを利用する．parserで作成したASTをCheckerが走査し，シンボル表と型情報を管理してチェックする．ts→Parser→AST→Checkerという流れ．走査中に
  - シンボル表を作る・参照する
  - 式の型を計算する
  - 文ごとにルールをチェックする

- 意味解析は構文が正しいことを前提にしているため，構文解析が成功したもののみ意味解析を行うとしてよい．

- 意味解析の中心は「シンボル表とスコープの管理」
  - スコープの管理
    - 内側のスコープで同じ名前を「別のもの」として宣言できる（シャドウイング）
    - 変数や手続きの「見える範囲」を正しく制限する
    - 実行時のスタックフレーム構造とも対応させられる

- ASTフォルダには意味解析ロジックを書かない＝ASTは構造を保存するために存在して，責務を分離する．つまり，ASTは純粋なデータ構造を持っていて，CheckerはASTを読むロジックを持つ．AST側にはinterfaceでvisit関数を用意しておく．acceptで呼ばれてvisitをAST側が返す．

- Vistorパターン
  - 説明：すでに出来上がったASTを上から順にみていく．識別子などの重複をシンボル表を更新していくことでチェックする．
  - メリット
  - ASTとの関係性：ASTの構造さえ認識していればよい．
  - acceptとvisitの関係性．acceptを使う意味：acceptでcheckerがASTに解析器を渡し，ASTがcheckerに適切なvisitパターンを返す．この双方向性によって，型がなんか得するらしい？？
  - R（ジェネリクス）の意味


- 工夫点・修正点
  - equalを修正して，型のチェックができるようにした．左辺と右辺をequalでチェックしても，それぞれのインスタンスのフィールドが一致していても，参照元が違うからこれは毎回falseになる．
  - スコープの管理で，lookupの実装方法を誤っていた．細心のスコープのみ参照していたが，実際は内側から外側へ向かってすべてのスコープを参照するべき．そうしないと，呼び出した関数内でグローバル変数などが参照できず，例外処理をしてしまう．
  - 引数の個数チェックでエラーが起きた．ProcDeclの引数Paramsは，リストが要素になることもあるため，すべての引数をそれぞれ分解して手続きの型リストに入れなければならない．
